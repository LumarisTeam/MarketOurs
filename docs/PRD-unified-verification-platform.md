# 统一人机验证与验证码平台 PRD

## 1. 概述

建设一个供多个业务接入的统一验证平台，提供滑块人机验证和一次性验证码服务。第一期以 MarketOurs 为接入对象，并为后续 iOS Club Website 接入预留独立的应用配置和接口。

平台负责验证能力；各业务仍负责自己的用户、登录状态和业务权限。

## 2. 背景

MarketOurs 当前已有自建滑块验证，并在注册、登录、找回密码等流程中使用验证码。随着社团官网也需要验证能力，各业务分别开发和维护会重复投入，规则也容易不一致。统一平台可以让业务复用验证流程，同时保留各自的配置和数据边界。

## 3. 目标与衡量

目标是让业务通过注册应用、配置验证方式和调用接口接入平台，减少重复开发，并保护发送验证码等操作。

以下为首版建议目标，需上线后确认基线和统计周期：

- MarketOurs 的注册、验证码登录和找回密码流程完成迁移，原有流程可正常使用。
- 使用两个独立应用配置完成隔离验收；iOS Club Website 可作为第二个接入应用，具体上线时间待定。
- 记录验证请求量、成功率、发送失败率及接口可用率，为后续设定可靠性目标提供基线。

## 4. 目标用户

- **业务开发者**：需要在 MarketOurs 和社团官网中快速加入验证，并独立配置业务场景。
- **平台管理员**：需要管理接入应用、发送渠道、用量和异常情况。
- **终端用户**：需要在注册、登录或找回密码时顺利完成人机验证和身份确认。

## 5. 价值主张

### 业务开发者

- **谁**：维护 MarketOurs 或社团官网的开发者。
- **为什么**：需要阻止自动化滥用，并确认用户能够接收验证码。
- **现状**：业务各自维护验证逻辑、渠道和规则，重复开发且难以统一排查。
- **如何实现**：按应用注册并通过统一组件和接口使用滑块及验证码能力。
- **之后**：新业务复用已有能力，同时保留独立配置。
- **替代方案**：继续各自实现，或分别接入第三方服务；统一平台适合需要多个业务共享管理的场景。

价值：一次建设验证能力，让多个业务以一致方式接入和维护。

### 平台管理员

- **谁**：负责验证平台运行与接入的管理员。
- **为什么**：需要控制哪些业务可使用平台，并了解发送和验证异常。
- **现状**：配置和运行信息分散在各业务中。
- **如何实现**：集中管理应用、渠道、配额和基础运行记录。
- **之后**：能够按应用定位问题并限制异常使用。
- **替代方案**：分别登录各业务或第三方控制台；统一平台减少跨系统管理。

价值：集中管理共享能力，同时按业务区分权限和用量。

### 终端用户

- **谁**：使用接入业务进行注册、登录等操作的人。
- **为什么**：需要完成验证后继续操作。
- **现状**：不同业务的验证体验和失败提示可能不一致。
- **如何实现**：提供清晰的滑块交互、验证码输入和可理解的失败提示。
- **之后**：用户知道何时重试或重新获取验证码。
- **替代方案**：使用各业务原有流程；统一体验的价值取决于易用性和稳定性。

价值：以清晰、一致的方式完成验证并继续使用业务。

## 6. 方案

### 6.1 核心流程

1. 管理员创建应用，配置允许的来源、验证场景、发送渠道和限额，并向业务安全提供接入凭据。
2. 业务前端请求并展示滑块验证；用户完成后获得短期有效的验证凭证。
3. 业务服务端提交凭证，由平台校验其应用、场景、有效期和使用状态；需要发送验证码的场景在校验通过后发起发送。
4. 用户输入收到的验证码，业务服务端请求平台校验；校验成功后由业务完成注册、登录或密码重置。
5. 过期、失败或超过限制时，用户获得明确提示；平台保留不包含验证码明文的操作记录供排查。

### 6.2 首版功能

| 优先级 | 功能 | 需求与验收要点 |
| --- | --- | --- |
| P0 | 应用管理 | 管理员可创建、停用应用，配置场景与允许的网页来源；每个应用使用独立标识和服务端密钥，支持密钥轮换。停用后拒绝新请求。 |
| P0 | 滑块人机验证 | 提供生成挑战、提交结果和服务端校验凭证的能力；凭证短期有效、限一次使用，并绑定应用和场景。失败可重试或刷新。 |
| P0 | 邮箱验证码 | 支持发送和校验一次性验证码，配置有效期、发送间隔及尝试次数；校验成功或过期后不可再次使用。首次支持现有邮件渠道。 |
| P0 | 场景与隔离 | 按应用和场景区分注册、登录、找回密码等用途；一个应用或场景的挑战、凭证及验证码不能用于其他应用或场景。 |
| P0 | 风险控制 | 按应用、接收地址和来源限制发送与验证频率；服务端鉴权，前端不保存服务端密钥。错误提示避免泄露验证码或密钥。 |
| P0 | 接入能力 | 提供接口文档与网页接入示例；MarketOurs 网页端、移动端及后端完成相关流程迁移，现有业务接口的兼容或切换方案在开发前确定。 |
| P0 | 运维记录 | 按应用和场景查看请求量、成功和失败数量；记录发送状态与错误原因，不记录验证码明文或完整敏感凭据。 |
| P1 | 短信渠道 | 在发送服务和业务配置上预留扩展；短信服务商、费用和上线时间另行确定。 |

### 6.3 技术与边界

平台作为独立服务提供接口；网页和移动端负责展示与交互，接入业务的服务端负责调用敏感接口。验证码发送与人机验证可按业务场景组合，但是否要求先完成滑块验证由平台配置并在服务端强制执行。平台不替业务签发登录会话，也不管理业务用户账号。

### 6.4 假设与待决问题

- 假设首版由内部管理员手动开通应用，不开放自助注册；是否需要管理后台，还是先通过受保护的管理接口配置，待确定。
- 假设首版邮件验证码覆盖现有主要场景；手机号验证码现有使用范围、短信渠道和预算需确认，迁移前不得中断已有能力。
- iOS Club Website 的实际业务场景、技术栈和预计接入时间待确认；目前仅要求平台支持其作为独立应用接入。
- 域名及移动端身份校验方式、部署环境、邮件模板归属、数据保留期限和可用性目标需在实施前确定。
- 滑块是否继续自建、切换第三方，或将两者作为可替换提供方，需结合安全性、成本和维护能力决策。

## 7. 发布计划

- **第一阶段**：确定接口和安全规则，完成平台核心能力与两个应用配置的隔离验收。
- **第二阶段**：迁移 MarketOurs，逐项验证注册、验证码登录和找回密码，并制定回滚方案；迁移时保留未覆盖的现有能力。
- **后续阶段**：按社团官网实际需求接入第二个业务，评估短信渠道、自助接入和更丰富的统计。

首版不建设统一用户中心、跨业务单点登录或面向公众的验证码商业平台。具体工期在确认部署方式、渠道和移动端接入方案后评估。
