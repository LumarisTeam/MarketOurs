# MarketOurs 多学校 PRD

**版本 0.1 · 评审稿**

## 1. 概述

MarketOurs 将从西建大单校集市扩展为多学校平台。师生从各自学校入口浏览内容、加入和互动，校管理员在本校范围内处理审核和举报。首版先迁移西建大，再通过同一套 Web、Flutter 和 API 开通第二所学校。

## 2. 背景

- 现有帖子、评论、标签、教师评价和举报的数据模型没有学校归属。后台以全局 `Admin` 角色保护管理入口，每日热榜从全站取榜和找收件人。开通第二所学校前，需要补齐数据和权限边界。 [数据模型](../api/MarketOurs.WebAPI/MarketOurs.Data/MarketContext.cs#L12) · [管理入口](../api/MarketOurs.WebAPI/MarketOurs.WebAPI/Controllers/AdminController.cs#L10) · [每日热榜](../api/MarketOurs.WebAPI/MarketOurs.DataAPI/Services/Background/DailyHotListBackgroundService.cs#L52)
- 西建大校园 OAuth 写死在服务配置中，Flutter 的反馈 SDK 也固定使用 `xauat`。现有公开帖子支持匿名访问，验证码登录可能自动创建账号。这些入口都需要学校规则。 [校园 OAuth](../api/MarketOurs.WebAPI/MarketOurs.WebAPI/Program.cs#L267) · [Flutter 初始化](../app/mobile_app/lib/main.dart#L24) · [帖子接口](../api/MarketOurs.WebAPI/MarketOurs.WebAPI/Controllers/PostController.cs#L22) · [验证码登录](../api/MarketOurs.WebAPI/MarketOurs.DataAPI/Services/LoginService.cs#L493)

## 3. 目标与衡量

让平台能够开通并运营第二所学校，同时让西建大用户继续使用原账号、内容和分享链接。以下为建议的首版验收指标。

| 关键结果 | 达标条件 | 验证时间 |
| --- | --- | --- |
| KR1 · 学校可独立运营 | 同一环境启用 2 所学校。每校均用真实或授权的试点账号，在 Web 和 Flutter 上完成各自适用的登录、浏览、搜索、发帖、评论、举报和通知流程，并由本校管理员完成审核。 | 第二校试点结束前 |
| KR2 · 学校边界正确 | 双校隔离用例 100% 通过。未经授权的跨校读写、后台操作及通知投递为 0。公开内容访问按已确认的可见性规则单独验收。 | 开放第二校前，扩大试点前复验 |
| KR3 · 西建大迁移连续 | 迁移清单内的历史记录 100% 有明确归属，抽样和自动核对均无关系或附件引用缺失。约定的原账号登录、旧版客户端和旧链接回归用例 100% 通过。 | 生产切换前演练，切换后复核 |

试点期间按学校记录准入验证完成率、发帖成功率、审核处理量、异常拒绝和推送失败量。试点数据用于建立使用基线，增长目标在取得基线后制定。

## 6. 方案

### 6.1 核心流程

1. 平台运营人员创建学校记录，设置名称、入口标识、准入方式和状态，给指定账号授予该校管理权限。第二校先只向受邀用户开放注册。
2. Web 用户从 `/s/{slug}`、选校页或带学校信息的分享链接进入。Flutter 用户可选校，也可从分享或推送进入；页面显示当前学校。
3. 用户在所选学校登录。新用户先完成学校准入，再建立账号和会话。校内账号切到其他学校页面时，可按目标学校的可见性规则浏览，写入操作需要对应学校的成员权限。客户端切校时按新学校加载页面与数据。
4. 用户在所属学校发帖、评论、举报。校管理员在本校后台处理，审核结果和相关通知按学校和收件人发送。
5. 学校不存在、尚未开放、已停用，或学校与会话不匹配时，页面提示原因并提供可用入口。校外资源的接口响应不暴露私有对象是否存在。

### 6.2 首版需求与验收

| 编号 | 功能 | 需求与验收标准 |
| --- | --- | --- |
| P0-01 | 学校开通与状态 | 平台管理员可通过受保护的管理入口创建、启用、停用学校，配置名称、唯一入口标识、加入方式及首位校管理员。停用后拒绝该校业务访问和新写入，停止校级定时任务与推送。保留数据，记录操作者、学校和操作结果。另一校继续运行。 |
| P0-02 | 注册与入校验证 | 第二校试点使用按校签发的邀请码，校方能提供可核验邮箱域时可启用邮箱验证。服务端验证邀请的学校、有效期和使用状态，校验邮件地址归属及验证码。主动注册、验证码登录自动建号和 OAuth 首次登录共用准入规则。西建大校园 OAuth 继续走现有入口。 |
| P0-03 | 登录与会话 | 账号登录、验证码、找回密码、OAuth 回调和刷新会话都按学校校验。登录态携带当前学校。另一校的验证码、注册凭证或刷新会话无法用于当前学校。切到其他学校的公开页面时，沿用目标学校的访客权限。 |
| P0-04 | 校内内容与交易交流 | 首页、热榜、标签、搜索结果及总数、帖子、评论、教师评价、个人主页和关注数据按学校限定。发帖、评论、点赞、关注、屏蔽和举报均校验操作者与目标资源同校。通过直接链接或对象 ID 访问也执行相同权限。 |
| P0-05 | 管理与平台权限 | 校管理员仅能查看和管理本校审核、举报、标签、用户及统计。平台管理员负责学校配置和授权。平台日志、全局封禁等平台级入口单独控制。记录角色授予、撤销、审核和学校停用等操作，后台页面与 API 权限一致。 |
| P0-06 | 附件 | 上传凭证绑定学校和用户，发帖引用、删除和清理校验归属。公开附件按发布内容的可见性规则访问。若启用成员专属内容，其附件经授权读取。验收同时检查页面、直接文件 URL 和旧链接。 |
| P0-07 | 通知、热榜和异步处理 | 审核、点赞同步和通知任务携带学校标识，任务执行时再次确认目标归属。每日热榜逐校生成并向本校收件人推送。任务重试与学校停用场景遵守相同规则。通知落地页能恢复对应学校。 |
| P0-08 | Web、Flutter 与旧入口 | Web 和 Flutter 可展示当前学校并进入其他学校的可访问页面。切校后首页、搜索、通知、表单和本地缓存均使用新学校上下文，原校未完成的请求不能覆盖新页面。过渡期旧路径和旧客户端的无学校请求仅解析为西建大。选校和分享链接能跨 Web 与 Flutter 使用。 |
| P0-09 | 运行监测与支持 | 按学校查看注册验证、发帖、审核、后台任务和推送结果；能定位迁移异常和异常的跨校拒绝。日志保留学校标识和请求关联 ID，避免记录验证码、邀请码或令牌明文。 |

### 6.3 技术方案与数据边界

- **共用应用和数据库。** 新增 `School` 及学校配置。学校内容、校内成员和用户关系使用 `SchoolId`。平台级配置由平台权限管理。保留历史主键，到数据库层约束帖子与评论、帖子与标签等关系的学校一致性。每校标签允许同名，数据库按学校约束标签名唯一，初始化使用独立 ID。
- **服务端解析学校。** 学校路径或 API 参数用于选定学校，服务端根据学校状态、访问策略和会话校验权限。业务查询通过带学校上下文的 DbContext 统一限定学校。每次从池中取得上下文时设置学校，写入和关联操作另做同校校验。PostgreSQL 的 ParadeDB 搜索与 SQLite 回退查询都在分页前限定学校。 [当前 DbContext 工厂](../api/MarketOurs.WebAPI/MarketOurs.WebAPI/Program.cs#L378) · [搜索实现](../api/MarketOurs.WebAPI/MarketOurs.DataAPI/Repos/PostRepo.cs#L287) · [EF Core 上下文池](https://learn.microsoft.com/en-us/ef/core/performance/advanced-performance-topics)
- **缓存和后台与数据库使用同一边界。** 以学校 ID 区分校内业务缓存、会话、验证码和分布式锁。任务从消息读取学校上下文，校级定时任务按启用学校执行。检查旧 Redis 键、待处理任务、上传凭证和设备推送注册的迁移策略。 [现有缓存键](../api/MarketOurs.WebAPI/MarketOurs.DataAPI/Configs/CacheKeys.cs#L7)
- **历史数据保留原标识。** 核对用户、内容、关系、通知与附件实际归属，把归属明确的单校历史数据迁入 `xauat`。历史管理员按职责重新授权，平台权限逐账号确认。无法自动确认归属的记录进入人工核对清单。

### 6.4 假设与待决问题

| 待决问题 | 估算采用的口径 | 决策时点及影响 |
| --- | --- | --- |
| 一个账号能否同时加入多校 | 首版一个账号归属一校，登录标识沿用平台账号口径，允许浏览按规则公开的外校页面。 | 数据模型设计前确认。若同时加入多校，使用账号与学校成员关系表，在成员关系保存角色和状态，扩展切校、会话和用户关系规则并重估。 |
| 外校及访客能看哪些内容 | 保留西建大现有公开内容的浏览方式。第二校优先通过邀请控制参与资格，公开或成员专属的可见性由试点校确认。 | 开发定范围前确认各校的帖子、教师评价、个人主页和附件可见性。成员专属内容需要鉴权读取附件。若西建大历史附件也改为私有，需评估存储迁移和旧链接处理。 |
| 第二所学校是谁、如何核验成员 | 按一个试点校、邀请码为主估算。邮箱域验证是否可用取决于试点校。 | 试点前落实学校、准入负责人和本校管理员。若首批要使用校方统一身份认证，需提前核对协议、测试账号和接入周期。 |
| 谁运营学校以及如何处理历史账号 | 平台内部开校，指定校管理员。暂按西建大单校历史估算回填量。 | 迁移演练前确认历史数据归属、角色清单、旧客户端兼容窗口和原有 OAuth 账号绑定。 |

### 6.5 双校验收

使用两所学校各一组普通账号、校管理员、同名标签和相似内容，另准备一个平台管理员账号。对 Web、Flutter 和 API 验收下列场景。

| 场景 | 预期结果 |
| --- | --- |
| 浏览公开内容和受限内容 | 访客和外校成员只能按目标校规则浏览公开内容。把帖子链接、附件 URL 或学校路径替换为另一校资源，响应仍符合目标资源的可见性。 |
| 搜索、热榜和切校 | 同一关键词、标签名或分页参数只返回当前学校的数据及计数。连续切校并命中缓存时，页面和响应仍属于选中的学校。 |
| 加入和登录 | 已使用、过期或属于另一校的邀请码和验证码均被拒绝。验证码自动建号、OAuth 回调与刷新会话执行同样的学校边界。 |
| 互动和后台管理 | 用甲校身份提交指向乙校的评论、点赞、关注、举报或后台操作，服务端拒绝且数据无变化。分别验证两校管理员可以管理本校。 |
| 通知和停用 | 运行两校的热榜、审核和通知任务，收件人与内容归属相符。停用其中一校后重试该校任务，拒绝相关业务访问及新增投递，另一校正常运行。 |
| 迁移与恢复 | 核对西建大各类记录数量、主键和引用。验证旧版客户端、旧链接、并行回填期间的写入，以及第二校产生新记录后的回滚演练。 |

## 7. 发布计划

| 阶段 | 工作内容 | 阶段出口 |
| --- | --- | --- |
| 方案确认与预发 | 确认账号和浏览规则，核对历史数据及角色，完成学校入口、数据隔离、两端适配和后台任务改造。准备西建大数据副本及两校测试数据。 | 双校验收通过，迁移演练结果满足 KR2、KR3。 |
| 西建大生产切换 | 备份并记录回滚点，新增归属字段、分批回填，核对数据后启用新查询和写入约束。刷新旧缓存，处理旧会话和待执行任务。优先兼容旧登录，无法安全映射的会话在切换时引导重新登录。 | 新旧入口、历史账号、审核和推送均通过生产复核。 |
| 第二校邀请试点 | 开通第二校并授权校管理员，邀请师生完成端到端操作，持续观察准入和通知。 | KR1–KR3 达标，并由试点方确认可扩大注册范围。 |

发现跨校数据暴露、越权写入、误推送或迁移核对失败时，暂停扩量。可按影响范围停用第二校入口、暂停受影响任务或回滚应用。数据迁移先做兼容性变更，收紧约束前演练回滚。第二校开始写入后，只回滚到已支持学校隔离的应用版本。需要恢复单校应用时，使用仅含西建大数据的数据库，并单独保全第二校新增数据。

按一名熟悉仓库的开发者估算，共 **17–25 人日，约 4–6 周**。按共享部署、单校账号和邀请试点估算，学校审批、各校统一身份认证对接及历史附件私有化迁移另计。

| 工作项 | 人日 |
| --- | --- |
| 学校入口与数据层 | 3–4 |
| 注册、登录与权限 | 4–6 |
| 内容、搜索、缓存与后台任务 | 4–6 |
| Web、Flutter 与管理后台 | 3–4 |
| 数据迁移、验证与试点 | 3–5 |

**后续范围**包括学校自助开通、自定义域名和品牌、多校成员身份、跨校交易与信息流，以及按校独立部署。是否启动这些功能，以试点需求和运营成本评估为准。
